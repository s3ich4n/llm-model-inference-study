## 서론: 왜 에이전트를 알아야 하나

2026년 3분기에 들어선 지금도 에이전트 애플리케이션은 LLM 기반 시스템을 만드는 기본 패턴입니다.
지식 어시스턴트, 코파일럿, 워크플로우 자동화, 추론 엔진 대부분이 에이전트형 구조를 따릅니다.

여기서 중요한 건 사용자 요청 하나가 끝이 아니라는 점입니다. 요청 하나가 여러 번의 LLM 호출과 검색,
도구 실행, 반복 추론을 촉발합니다. 그래서 서빙 쪽에서 이런 일이 생깁니다.

- 토큰 사용량이 늘어난다
- 호출이 체인으로 이어지면서 tail latency가 증폭된다
- 연산 패턴이 동적으로 바뀐다
- 모델과 도구 사이를 조율(오케스트레이션)해야 한다

책 후반부에 나오는 캐싱, 배칭, 메모리 관리, 스케줄링, 병렬화 같은 최적화 기법은 전부 이
"에이전트 워크로드"를 감당하기 위한 것입니다. 그래서 에이전트 구조를 먼저 이해해야 뒤 내용이 붙습니다.

## 본론

### 1. 무엇이 달라지는가: 예측 엔진에서 제어 루프 안의 부품으로

2~3장까지 모델은 독립적인 예측 엔진이었습니다. 요청 하나에 추론 한 번, 응답 반환.

에이전트에서는 이 전제가 깨집니다. 모델이 에이전트 시스템 안에 내장되고, 제어 루프(control loop)
안에서 반복 호출됩니다. 루프를 돌면서 정보를 검색하고, 중간 결과를 추론하고, 도구를 실행하고,
출력을 다듬은 다음에야 최종 답이 나옵니다.

에이전트의 정의는 다음이 가능한 자율적 LLM 기반 시스템입니다.

1. 상위 수준 목표를 이해한다
2. 그 목표를 달성할 방법을 추론한다
3. 외부 도구나 데이터 소스를 골라 호출한다
4. 중간 결과를 보고 적응하고 반복한다
5. 사람 개입을 최소로 두고 최종 결과물을 낸다

규칙 기반 챗봇 같은 전통적 시스템은 개발자가 미리 짜둔 워크플로우를 따라갑니다.
차이의 본질은 자율성입니다. "무엇을 어떻게 할지"까지 시스템이 스스로 정한다는 점.

### 2. 그래서 서빙이 감당해야 하는 것

모델 성능이 좋아져서 단독으로 해결되는 일도 늘었습니다. 그래도 실제 에이전트에는 여전히
다중 LLM 호출, 더 긴 컨텍스트 윈도우, 검색 연산(RAG), 메모리 재사용(CAG)이 필요합니다.

그러므로 모델 서빙은 모델을 효율적으로 실행하는 일을 넘어, 오케스트레이션과 메모리 관리,
시스템 수준의 조정까지 지원해야 하는 일이 됩니다.

**tool call: 인터넷 검색은 누가 실행하나**

모델은 인터넷 검색을 직접 못 합니다. 대신 "이 도구를 이런 인자로 불러줘"라는 tool call을 뱉고,
누군가 그걸 실제로 실행해서 결과를 다시 모델에 넣어줍니다. 실행 주체에 따라 세 가지로 나뉩니다.

| 실행 위치 | 동작 | 장점 |
| --- | --- | --- |
| 클라이언트 | 애플리케이션이 모델의 tool call을 직접 실행 | 실행 흐름을 세밀하게 제어 |
| AI gateway | gateway가 tool call을 가로채 실행 | 여러 모델에 공통 정책 적용 |
| AI provider | 모델 제공 서비스가 검색 도구까지 실행 | 구현이 줄어듦, 대신 provider 지원 범위에 의존 |

핵심은 tool call을 어디서 실행하고 결과를 어떻게 다시 전달하느냐입니다.

> LiteLLM은 여기서 gateway 자리에 해당합니다. 여러 provider의 API를 하나의 인터페이스로 묶고,
> 라우팅과 폴백, API 키 관리, 예산·사용량 제한을 대신 처리합니다. 모델 자체를 관리한다기보다
> "모델 호출을 관리하는 계층"에 가깝고, 그 위에서 tool call 처리 같은 공통 정책을 얹을 수 있습니다.

### 4. 데모: RAG 기반 지식 에이전트

지금 디렉터리(`ch04/basic_rag_study`)의 코드가 그 예제입니다. 로컬 모델이나 별도 DB 없이
OpenAI API(LLM 추론 + 임베딩)만 쓰고, 모든 정보를 인메모리에 둡니다. `knowledge_files/`에 PDF를
넣어두면 기동할 때 자동으로 처리합니다.

구성 요소는 다섯 개입니다.

```
사용자 질문 → Agent.process_query()
              ├─ Planner (LLM) → 실행 계획 수립
              └─ ActionExecutor 순차 실행
                    ├─ RAGSystem (임베딩 모델) → 관련 문서 검색
                    └─ LLMManager (LLM) → 각 액션별 응답 생성
```

- Agent: 전체를 조율하는 중앙 컨트롤러
- RAGSystem: PDF를 청크로 쪼개고 임베딩을 만들고 벡터 검색을 수행
- Planner: LLM을 써서 실행 계획을 세움
- Actions: 질의, 요약, 분석 같은 구체적 작업을 실행
- LLMManager: OpenAI API 호출과 토큰 관리

여기서 짚어둘 점 하나. RAG는 모델에 넣을 input을 augmentation 하는 것뿐입니다.
LLM 입장에서 RAG는 프롬프트 텍스트가 길어진 것에 지나지 않습니다. 검색해서 붙였든 사람이
복사해 붙였든 모델은 구분하지 못합니다. "검색된 문서가 attention의 Q 행렬에 주입된다"는 식의
직관은 틀렸습니다.

```
사용자 query
    ↓  [embedding model]
query 벡터
    ↓  [Vector DB, cosine similarity]
top-k 문서 텍스트
    ↓
──────────────────────────────
여기부터는 그냥 텍스트 합치기

prompt = f"""
{retrieved_doc_1}
...
Question: {query}
"""
──────────────────────────────
    ↓  [LLM]
토큰화 → X(입력 임베딩 행렬)의 row가 늘어남 → 평소와 똑같은 self-attention → 응답
```

덧붙여, 2단계(분석)에서는 임베딩 호출이 없었습니다. 1단계 요약 결과가 그대로 다음 액션의

분석을 쓴 것입니다.

### 5. 에이전트 자율성은 어떻게 만들어지나

**액션(Actions)**

자율성을 떠받치는 건 재사용 가능한 액션 집합입니다. 가짓수가 딱 떨어지게 셀 수 있는,
서로 명확히 구분되는 유한한 행동들입니다. 이 예제에서 `planner.py`가 들고 있는 액션은 네 개뿐입니다.

```python
self.available_actions = [
    "query_rag_with_context",
    "generate_profile_based_response",
    "generate_summary",
    "generate_analysis",
]
```

각 액션은 `actions.py`에서 "LLM 호출 + 특화된 프롬프트 템플릿"으로 구현됩니다.
예를 들어 분석 액션의 프롬프트는 질문과 컨텍스트를 묶어 근거 기반 분석을 하도록 만듭니다.

```python
def create_analysis_prompt(self, query: str, context: str) -> str:
    prompt = f"""
You are an expert analyst. Please provide a detailed
analysis of the following question based on the
provided context.

Question: {query}

Context:
{context}

Please provide:
1. A comprehensive analysis
2. Key insights and findings
3. Relevant examples from the context
4. Any limitations or gaps in the available information

Analysis:
"""
    return prompt
```

이 예제는 일부러 LLM 호출만 쓰는 단순한 구조를 유지합니다. 실제 에이전트의 액션은 LLM 프롬프트에
국한되지 않습니다.

- 도구 호출: 웹 검색, API 질의, DB 명령 실행
- 시스템 연산: 파일 관리, 워크플로우 트리거, 외부 서비스 연동
- 추론 단계: 사용자에게 보이지 않는 중간 계산이나 계획 서브루틴

**LLM 기반 플래닝 (`planner.py`)**

미리 짜둔 워크플로우 대신, LLM에게 고수준 지시를 해석시켜 서브태스크로 쪼개고 실행 순서를
정하게 합니다. 사용자가 "PDF 파싱하고, 관련 섹션 찾고, 결과 요약해줘"를 손으로 지시하지
않아도 되게 만드는 부분입니다.

```python
def create_plan(self, query: str) -> Dict[str, Any]:
    planning_prompt = self.llm_manager.create_planning_prompt(
        query, self.available_actions
    )
    plan_response = self.llm_manager.generate_response(
        planning_prompt, temperature=0.3
    )
    plan = self._parse_plan_response(plan_response)
    return plan
```

응답 파싱이 실패하면 `_create_fallback_plan()`이 키워드 매칭으로 대체 계획을 만듭니다
("what/how"면 RAG 1스텝, "summarize"면 RAG + 요약 2스텝). 플래닝이 실패해도 완전히 멈추지 않게
하는 장치입니다.

실행 로그에서 재미있었던 지점 하나. "What is X and how does it work?"는 폴백 규칙대로라면
`["query_rag_with_context"]` 1스텝으로 갔을 질문인데, LLM 플래너가 살아 있어서
`["generate_summary", "generate_analysis"]` 2스텝을 스스로 골랐습니다. 하드코딩된 휴리스틱과
다른 판단을 실제 로그로 확인한 셈입니다.

**MCP: 도구 사용의 표준화**

Model Context Protocol은 에이전트가 외부 도구, 데이터 소스, 애플리케이션과 표준 방식으로
연결되게 하는 프로토콜입니다. LLM이 쓸 수 있는 도구를 발견하고, 구조화된 입력으로 호출하고,
결과를 추론 과정에 다시 반영하는 인터페이스를 통일합니다. 도구 정의를 에이전트 핵심 로직에서
떼어내니 개발이 단순해지고, 그때그때 프롬프트로 때우는 방식의 취약함도 줄어듭니다.

에이전트 워크플로우가 늘어날수록 도구 인터페이스를 잘 다듬는 일과 권한 경계를 잘 긋는 일이
중요해집니다.

### 6. RAG와 CAG

**RAG (Retrieval-Augmented Generation)**

질문할 때 필요한 자료를 찾아서 LLM에 같이 넣어주는 방법입니다. LLM 단독의 한계 세 가지를 덜어줍니다.

1. 지식이 고정적이다. 학습 데이터 컷오프 이후 정보가 없다
2. 환각. 그럴듯하지만 사실과 다른 내용을 만든다
3. 도메인 특화 지식이나 최신 정보가 부족하다

RAG 시스템은 두 갈래 워크플로우로 나뉩니다.

- 인덱스 빌딩 (오프라인, 주기적 실행): 원본 문서를 정제하고 파싱해서 일반 텍스트로 바꾸고,
  보통 1,000토큰 정도의 청크로 쪼갠 다음, 청크별 임베딩을 미리 대량으로 계산해 벡터 DB에 넣습니다.
  청킹은 단순 전처리가 아니라 검색이 얼마나 잘게 이뤄질지를 정하는 결정이고, 오프라인 배치
  추론이 일어나는 지점이기도 합니다.
- 질의/검색 (온라인, 실시간): 쿼리 텍스트를 임베딩하고, 코사인 유사도로 가까운 벡터를 찾고,
  해당 청크를 쿼리와 함께 LLM에 넘겨 답을 만듭니다.

청킹 크기는 트레이드오프입니다. 작은 청크는 검색 정밀도가 올라가지만 문맥이 잘릴 수 있고,
큰 청크는 문맥이 풍부한 대신 관련 없는 내용이 섞여 정밀도가 떨어집니다. 최적값은 도메인과
LLM 컨텍스트 윈도우에 따라 달라집니다.

청킹이 필요한 이유는 결국 컨텍스트 윈도우 때문입니다. LLM은 입력과 출력을 합쳐 한 번에 처리할 수
있는 토큰 수에 상한이 있어서, 문서 전체가 아니라 관련성 높은 조각 몇 개만 골라 보내야 합니다.

이 예제는 이 과정을 단순화해서 `agent.py`를 띄울 때마다 인메모리로 다시 빌드합니다.
테스트를 네 번 돌리면 42개 청크를 네 번 다시 임베딩합니다.

비유하자면 RAG는 오픈북 시험입니다. 매 요청마다 책에서 찾아 답안에 첨부합니다.
반대 방향인 파인튜닝은 암기이고, 가중치에 지식을 새깁니다.

**CAG (Cache-Augmented Generation)**

RAG는 강력하지만 대가가 있습니다.

- 지연이 붙는다. LLM 호출 전에 "쿼리 임베딩 → 유사도 검색" 단계가 끼어든다
- 잘못 고를 위험이 있다. 제한된 토큰 안에서 가장 관련 있는 문서만 골라야 한다
- 시스템이 복잡해진다. 임베딩, 인덱스, 벡터 DB를 만들고 유지해야 한다

컨텍스트 윈도우가 커지면서 "몇 개만 골라 넣는다"는 RAG의 전제 자체가 흔들립니다. 지식 베이스
전체를 통째로 컨텍스트에 넣을 수 있다면 복잡한 검색 시스템 없이도 같은 문제를 풀 수 있습니다.

CAG는 쿼리 시점에 검색하는 대신, 지식을 미리 LLM의 KV 캐시에 올려두고 추론할 때 그 캐시된
컨텍스트로 바로 답합니다. 검색 지연이 사라지고 시스템도 단순해집니다. 대신 큰 컨텍스트 윈도우와
캐시 관리는 메모리와 연산 요구량을 늘립니다(이 최적화는 7장에서 다룹니다).

**비교**

| | RAG | CAG |
| --- | --- | --- |
| 지식 주입 시점 | 쿼리마다 동적 검색 | 미리 캐시에 로드 |
| 강점 | 최신성, 지식이 자주 바뀌는 경우 | 반복 질의, 고정된 지식 집합에서 지연 감소 |
| 개선하는 축 | 답변 품질(지식 접지, 최신성) | 서빙 효율(지연, 처리량, 비용) |
| 비용 | 검색 인프라 + 검색 지연 | 메모리와 캐시 관리 부담 |

양자택일이 아닙니다. RAG로 입력을 보강하고, CAG로 실행을 최적화하는 조합이 자연스럽습니다.

## 결론

1. 지금까지 본 모델과 도구는 결국 HTTP/gRPC API 같은 모델 서빙 서비스를 통해 온디맨드로
   호출됩니다.
2. 에이전트는 사람과 주고받으며 실시간으로 동작하기 때문에, 고성능·저지연·비용 효율적인 서빙이
   에이전트 애플리케이션 성공의 핵심 조건입니다.
3. 에이전트 애플리케이션에서 모델과 도구가 어떻게 쓰이는지 봤으니, 이 장의 나머지에서는 실제
   서비스에 쓰이는 프로덕션급 모델 구축 접근법을 살펴봅니다.
